# 図解の作り方

このサイトの図解（`/explainers/<名前>/`）を作るときの観点。**下の「指摘された失敗」は、実際にこのリポジトリの図解で
読者から指摘されたもの**で、同じ指摘を二度受けないために置いてある。

## 図解の目標

**そのページだけで、初めて見る人が仕組みを理解できること。**関連リポジトリへのリンクは入れるが、
リンク先を読まないと分からない図解は失敗。

## 指摘された失敗と、守ること

### 1. 前提知識が足りない（「P2 とかいきなり言われても分からない」）

- **元のプロジェクトの内輪の記号・略語を使わない。**「P2」「F1」「門番」のような名前は、役割で言い換える
  （「後退解析の関数」「手を作る関数」）。どうしても使うなら、初出の前に定義する
- **冒頭に「前提」を置く。**何のプログラムか、どこで時間を使っているか、出てくる用語（関数・命令・番地など）、
  数字の意味（「区間」など）を、カード数枚で先に渡す
- 本文の言葉は、前提で定義した言葉だけで書けているかを読み直す

### 2. 文字が途切れる（「hugeAll… が途切れていて分からない」）

- **ラベルを省略記号で切らない。**箱を広げるか、文字の大きさを箱の幅に合わせて自動で決める
- **動く図では、すべての状態で文字が収まるか確かめる。**つまみの最小・最大・途中で、箱の大きさが変わる

### 3. 動く値のラベルがはみ出す（「+1 バイト伸びた の + が見えない」）

- **大きさが変わる図形の中に、動く値のラベルを置かない。**値が小さいと図形が狭くなり、はみ出して切れる
- ラベルは図形の外の、いつも空いている場所に置く（例: 帯の上の余白）

### 4. 見るべき部分が分からない（「境目をまたいでいるように見えないか？」）

- **判定の基準になる線（境目・目盛り）は、図形の上に描く。**図形の下に描くと隠れて、またいでいるか読めない
- **判定しているのが図のどの部分かを、本文で明示する。**大きい箱（関数全体）と小さい箱（ループ）が重なって
  いるなら、どちらを見るのかを書く
- **判定の結果は、図の上に印で出す**（またいだ所に赤い線と「ループが境目をまたぐ」など）。数字の表示だけに頼らない

### 5. 「直した状態」が直っていないように見える（「直した配置なのにまたいでいる。例として破綻していないか」）

- **ボタンや見出しが約束していることと、図が見せていることを一致させる。**「直した配置」を押したら、
  直ったように見えなければならない
- 例外や注意（「揃えても実物ではまたぐことがある」）は、**本文の文章で**伝える。主題を否定する絵で見せない
- 模型の数値を選ぶときは、主題（「直すと動かなくなる」）がいちばん伝わる例を選ぶ。そのうえで、
  模型であること・たまたまそうなったことを本文に書く

### 6. 並びが気持ち悪い（「3つ並んで4つ目だけ下になっている」）

- **カードの列の数は、カードの数を割り切れる数にする**（4枚なら2列）。「幅に入るだけ並べる」設定は、
  広い画面で3枚＋1枚のような半端な行を作る
- 狭い画面では1列に落とす

### 7. 文字どうしが重なる

- 図の端（目盛りの最後の数字と単位など）で、文字が重ならないかを見る。単位は凡例に回してもよい

## 作るときの手順

1. **主題を1文で書く**（例:「関数の置き場所がずれると、同じ命令でも遅くなる。熱い関数をまとめて揃えると、ずれなくなる」）
2. **前提に要る言葉を書き出す。**読者が知らない言葉は、前提のカードか本文の初出で定義する
3. **場面を数珠つなぎにする。**1つの図（帯など）を最初から最後まで画面に置き、段階ごとにその図を動かして話を進める。
   場面が切り替わるだけのスライドにしない
4. **触れる操作を1つ入れる**（つまみ・切り替えボタン）。読者が自分で動かして確かめられること
5. **模型の数値は、計算で検算する。**本文に書く主張（「6バイトか7バイトかで変わる」「10バイトで片方だけまたぐ」
   「直した配置では両方収まる」など）を、模型の式で1つずつ確かめてから書く
6. **模型であることを書く。**実物の値ではないこと、図で省いた仕組み（実際の CPU では…など）を、ページ末尾に注記する
7. **元のプロジェクトへのリンクを入れる**（冒頭の小見出しと、末尾の注記）。ただしリンク先を読まなくても分かるように書く

## 仕上げる前の確認（全部やる）

- [ ] 動く図を、すべての状態で見た（つまみの最小・最大・途中、ボタンの両方、自動再生の途中）
- [ ] すべての状態で、文字が途切れず・はみ出さず・重ならない
- [ ] 判定の基準になる線が、図形の上に見えている
- [ ] ボタン・見出しが約束していることを、図が見せている
- [ ] 本文の主張を、模型の式で検算した
- [ ] 内輪の記号・略語が、定義なしに出てこない
- [ ] カードや並びに、半端な行が無い
- [ ] スマホの幅（約 400px）で、横スクロールが図の中だけに収まる
- [ ] ライトとダークの両方で読める
- [ ] `prefers-reduced-motion` のときに、動きを止める

## サイトに置く形

サイトは Astro でビルドする。動く部分は React の部品にし、動かない部分は Astro のページに HTML で書く。
見本は「関数の置き場所ラボ」（`src/components/hot-layout/` と `src/pages/explainers/hot-layout/index.astro`）。

| 置く場所 | 中身 |
|---|---|
| `src/components/<名前>/model.ts` | 模型の計算。画面に依存させない（検算しやすく、図解と記事の両方で使える） |
| `src/components/<名前>/*.tsx` | 動く部品（React）。状態を持たない描画の部品と、状態を持つ外側の部品に分ける |
| `src/components/<名前>/<名前>.css` | 見た目。**1つのクラス（例 `.hl`）の中に閉じ込める**（サイトのほかのページに漏らさない） |
| `src/pages/explainers/<名前>/index.astro` | 図解のページ。前提のカードと注記は HTML で書き、動く部品だけを `client:load` で読み込む。レイアウトは `Base` を `wide` で使う |
| `src/content/posts/YYYY-MM-DD-<名前>.mdx` | 紹介の記事。front matter は `title`・`date`（`+0900` を付ける）・`description`。記事の中にも部品を置ける（`client:visible`） |

- **外部から読み込むのは Google Fonts だけ。**ライブラリは npm で版を固定して入れる（`npm install --save-exact`）。
  React の部品から使うなら `import` する（Astro が束ねる）。素の `<script>` から使うなら `tools/vendor.mjs` の表に足し、
  `/vendor/<名前>/...` から読む。外部の `<script src>` は公開前検査（S7）が止める
- 冒頭の小見出しに、元のプロジェクトへのリンクを入れる（サイトのトップへのリンクはレイアウトのヘッダにある）
- 記事の日付は実際の時刻にする。**Astro は未来の日付の記事も出す**（Jekyll と違う）。下書きは `draft: true`（ビルドでは出ない）
- ローカルで確かめる: `npm run dev` → `http://localhost:4321/explainers/<名前>/`。保存すると画面がすぐ変わる
- 仕上げに `npm run check`（型）と `npm run build` を通す
