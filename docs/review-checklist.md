# 公開前レビューの観点

`tools/publish_lint.py` は「出したら取り消せないもの」のうち、機械で見つけられる形だけを止める。
機械に持たせられない残りをここに置く。スキル `review-before-push` がこれを読む。

## 優先順位

| | 種類 | 扱い |
|---|---|---|
| A | 公開すると取り消せないもの（個人や機械の特定・秘密・公開していないものの名前・写り込み） | **push しない**。直してからコミットを作り直す |
| B | 直せば済むもの（説明の誤り・図の不具合・誤字・デザイン） | 直すが、push は止めない |

B を A に混ぜない。止めない指摘を A に積むと、鳴っても押し切る癖がつく。

## A: 機械が見落とす、取り消せないもの

`publish_lint.py` は決まった形（パス・メール・IP・鍵の形・一覧にある言葉）しか見ない。次は目で見る。

- **画像の中身。**画面写真に、ユーザ名・パス・タブ名・ほかのウィンドウ・通知が写っていないか。
  `publish-allow.txt` に登録する前に、拡大して隅まで見る
- **出力の貼り付け。**ノートブックやターミナルの出力（`pip install` の行、エラーの traceback、
  プロンプトの `user@host`）を HTML に変換して貼っていないか。パスの形をしていない環境の情報
  （仮想環境の名前、公開していないリポジトリの名前、社内のサービス名）も出る
- **公開していないものの名前。**公開していないリポジトリ・サービス・人の名前を、本文・リンク・
  コメント・コミットメッセージに書いていないか（一覧に足していない名前は機械が見落とす）
- **例示が実データでないか。**実データで動かした出力を、そのまま例示に使っていないか。例示は架空のデータで作る
- **内輪の呼び名。**手元の機械の呼び名などを公開物に書いていないか。消すときに、1台の構成を
  環境全体の性質として書き直していないか
- **他人の情報。**共同作業の相手の名前やアカウント、私的なやりとりを載せていないか
- **古い作品の中身。**`public/legacy/` や `src/legacy/` に置いた HTML（ノートブックの書き出しなど）を足したら、
  出力欄まで読む。`pip install` の結果や警告に、パス・仮想環境・公開していないリポジトリの名前が出る

## B: 図解と記事

図解は [`docs/explainer-guide.md`](explainer-guide.md) の「仕上げる前の確認」を全部当てる。
そのうえで、ここでは次を見る。

- **主張と図が一致しているか。**本文が言っていることを、図が本当に見せているか。数値の主張は模型の式で検算できるか
- **リンク先を読まなくても分かるか。**内輪の記号・略語が定義なしに出てこないか
- **リンクが生きているか。**サイト内のリンクと外部リンクを開く
- **1つの記事で完結しているか。**図解が記事の中に直接あるか（別のページへ飛ばしていないか）。記事の日付が未来になっていないか
- **テスト。**`npm test` と `npm run test:e2e` が通るか（CI でも走り、落ちたら公開しない）
- **ビルドの出力。**`npm run build` のあと `python3 tools/publish_lint.py --dir dist` が通るか（GitHub Actions も同じ検査をする）。
  Astro は `src/pages/` と `public/` からしか出力しないので、`tools/`・`docs/`・`CLAUDE.md` は出ない。`public/` に置いたものは**そのまま全部出る**

## 読み方

- **主張を見たら、その対象を開く。**「〜を直した」「〜が収まる」と書いてあったら、その状態を実際に表示して確かめる
- **動くものは、すべての状態を見る。**最初の状態だけ見て通さない
- **同じ数字・同じ文言を2か所以上に書いたら、全部を grep する。**図解の本文・記事の front matter（description）・コミットメッセージ
